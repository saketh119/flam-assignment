# Part B2 — Long-Context Throughput Anomaly

## Evidence

The benchmark contains the following rows for the long-context workload, where:

```text
prompt_len = 3584
gen_len = 512
```

| Batch | Reported tok/s | KV utilization | Preempted sequences | TTFT p50 | E2E p95 |
|---:|---:|---:|---:|---:|---:|
| 16 | 1311.4 | 0.62 | 0 | 498.3 ms | 54.60 s |
| 24 | 1607.4 | 0.93 | 0 | 500.5 ms | 69.22 s |
| 32 | 1384.0 | 0.97 | 7 | 636.9 ms | 97.47 s |
| 48 | 1298.5 | 0.97 | 23 | 955.4 ms | 105.43 s |

The evidence was extracted with:

```text
python partB\b2.py
```

## The anomaly

The naive expectation is that increasing batch size should continue to increase throughput.

However, throughput peaks at batch 24:

```text
batch 24 = 1607.4 tok/s
batch 32 = 1384.0 tok/s
batch 48 = 1298.5 tok/s
```

Therefore, increasing the batch beyond 24 actually reduces the reported throughput.

## Quantifying the deviation from linear scaling

Use batch 24 as the baseline.

At batch 32, linear scaling would predict:

```text
1607.4 × (32 / 24)
= 2143.2 tok/s
```

The observed value is:

```text
1384.0 tok/s
```

The shortfall is:

```text
2143.2 - 1384.0
= 759.2 tok/s
```

Percentage below the linear expectation:

```text
759.2 / 2143.2 × 100
≈ 35.4%
```

Therefore, batch 32 is approximately 35.4% below the linear-scaling expectation.

For batch 48:

```text
1607.4 × (48 / 24)
= 3214.8 tok/s
```

The observed value is:

```text
1298.5 tok/s
```

The shortfall is:

```text
3214.8 - 1298.5
= 1916.3 tok/s
```

Percentage below the linear expectation:

```text
1916.3 / 3214.8 × 100
≈ 59.6%
```

Therefore, batch 48 is approximately 59.6% below the linear-scaling expectation.

## Mechanism

The strongest evidence points to KV-cache pressure.

At batch 24:

```text
KV utilization = 0.93
preempted sequences = 0
```

At batch 32:

```text
KV utilization = 0.97
preempted sequences = 7
```

At batch 48:

```text
KV utilization = 0.97
preempted sequences = 23
```

The increase in concurrency therefore pushes the system into a high-KV-utilization regime where sequence preemption occurs.

This is accompanied by significant latency increases.

From batch 24 to batch 32:

```text
TTFT:    500.5 ms → 636.9 ms
E2E p95: 69.22 s → 97.47 s
```

At batch 48:

```text
TTFT:    955.4 ms
E2E p95: 105.43 s
```

The evidence therefore supports the following mechanism:

```text
larger batch
      ↓
higher KV-cache utilization
      ↓
KV-cache pressure
      ↓
sequence preemption / scheduler overhead
      ↓
higher latency
      ↓
throughput no longer scales linearly
```

The benchmark directly establishes the relationship between high KV utilization, preemptions, increased latency, and degraded throughput. The exact internal implementation cost of preemption should be confirmed with a serving-stack metric in B4.

## Configuration/deployment change

For the 3584-token long-context workload, cap concurrency at:

```text
max_num_seqs = 24
```

instead of allowing concurrency to increase to 32 or 48.

The reason for choosing 24 is that the benchmark already demonstrates that this operating point achieves:

```text
reported throughput = 1607.4 tok/s
KV utilization      = 0.93
preempted sequences = 0
```

By contrast, batch 32 and batch 48 introduce preemptions and lower throughput.

## Predicted quantitative effect

The expected operating point is approximately:

```text
reported throughput ≈ 1607 tok/s
preemptions ≈ 0
```

for this benchmark workload.

The purpose of the cap is not to maximize nominal batch size. It is to keep the workload below the observed KV-cache/preemption knee, where additional concurrency begins reducing throughput and substantially increasing latency.

## Conclusion

The long-context throughput anomaly is not evidence that larger batches are inherently worse. Rather, the benchmark shows a capacity knee around batch 24.

Batch 24 reaches 1607.4 reported tok/s with zero preemptions. Increasing to batch 32 produces a 35.4% shortfall from linear scaling and introduces 7 preempted sequences. Batch 48 is 59.6% below linear scaling and has 23 preempted sequences.

A practical deployment change is therefore to cap long-context concurrency at 24 sequences until additional serving-level evidence supports a higher limit.
