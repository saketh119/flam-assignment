# Part B1 — KV-Cache Capacity

## Model specification

The FLM-4B-Instruct model has:

- Layers = 28
- Query attention heads = 24
- KV heads = 8
- Head dimension = 128
- KV cache precision = FP16
- GPU memory = 24 GB
- GPU memory utilization = 0.92
- Non-KV runtime overhead = 1.6 GB
- Maximum model length = 4096 tokens

The model uses grouped-query attention (GQA), so the KV cache uses 8 KV heads rather than 24 query heads.

## KV-cache bytes per token

For every token, the cache stores both a key and a value vector.

The exact formula is:

```text
KV bytes/token
= layers × 2 (K + V) × KV heads × head_dim × bytes_per_element
```

Substituting the model specification:

```text
= 28 × 2 × 8 × 128 × 2
= 114,688 bytes/token
```

Therefore:

```text
114,688 bytes/token = 112 KiB/token
```

So each additional token in the KV cache requires approximately 112 KiB.

## KV memory for one 4096-token sequence

For a full 4096-token sequence:

```text
114,688 × 4096
= 469,762,048 bytes
```

Therefore:

```text
469,762,048 bytes = 448 MiB
```

A single fully cached 4096-token sequence therefore requires approximately 448 MiB of KV cache.

## Approximate maximum concurrent sequences

The GPU has 24 GB of memory and the configured GPU memory utilization is 0.92.

Available memory under this utilization:

```text
24 GB × 0.92
= 22.08 GB
```

Subtracting the stated 1.6 GB non-KV runtime overhead:

```text
22.08 GB - 1.6 GB
= 20.48 GB
```

Using the simplified memory calculation:

```text
20.48 GB / 469,762,048 bytes
≈ 43.6
```

Therefore, the simplified theoretical capacity is approximately:

```text
43 full 4096-token sequences
```

This is an upper-bound calculation rather than a prediction of the exact serving scheduler capacity.

## Comparison with the benchmark

The long-prompt benchmark uses:

```text
prompt_len = 3584
gen_len = 512
```

Therefore:

```text
3584 + 512 = 4096 tokens
```

The relevant benchmark rows are:

| Batch | KV utilization | Preempted sequences |
|---:|---:|---:|
| 16 | 0.62 | 0 |
| 24 | 0.93 | 0 |
| 32 | 0.97 | 7 |
| 48 | 0.97 | 23 |

The theoretical calculation suggests that approximately 43 full 4096-token sequences could fit under the simplified memory model. However, the benchmark shows preemptions already at batch 32.

This does not necessarily contradict the calculation because the theoretical calculation ignores serving-stack details such as KV-cache block allocation, fragmentation, scheduler requirements, and other runtime memory behavior.

The observed benchmark therefore shows that the simplified theoretical capacity should be treated as an upper bound, not as a safe production concurrency limit.

## Conclusion

The model requires exactly:

**114,688 bytes/token = 112 KiB/token**

for its KV cache.

A 4096-token sequence requires:

**469,762,048 bytes = 448 MiB**

of KV cache.

Under the simplified memory assumptions, this gives approximately:

**43 concurrent 4096-token sequences**

as a theoretical upper bound.

The benchmark indicates that practical KV-cache pressure appears earlier, with preemptions beginning at batch 32 for the long-context workload.
