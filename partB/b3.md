# Part B3 — Honest Goodput

## Misread column

The report misinterpreted the `reported_tok_s` column as generated/output-token throughput.

For the batch-24 long-prompt row:

```text
batch_size     = 24
prompt_len     = 3584
gen_len        = 512
wall_clock_s   = 61.16
reported_tok_s = 1607.4
```

The reported value can be reconstructed as:

```text
24 × (3584 + 512) / 61.16
= 1607.33 tok/s
```

This matches the reported value of 1607.4 tok/s after rounding.

Therefore, the reported throughput counts:

```text
prompt tokens + generated tokens
```

rather than generated tokens alone.

## Honest batch-24 goodput

### Method 1 — direct calculation

Actual generated tokens are:

```text
24 × 512
= 12,288 output tokens
```

Dividing by wall-clock time:

```text
12,288 / 61.16
= 200.92 output tok/s
```

Therefore:

**Honest output goodput = 200.92 tok/s**

### Method 2 — correcting the reported throughput

The reported metric counts 4096 tokens per request:

```text
3584 + 512 = 4096
```

The fraction corresponding to generated tokens is therefore:

```text
512 / 4096
= 0.125
```

Correcting the reported throughput:

```text
1607.4 × (512 / 4096)
= 200.93 output tok/s
```

Therefore:

**Honest output goodput = 200.93 tok/s**

The two independent calculations agree to rounding:

```text
Method 1 = 200.92 tok/s
Method 2 = 200.93 tok/s
```

So the honest batch-24 output goodput is approximately:

**200.9 generated tokens/s**

rather than 1607.4 output tok/s.

## What the report should have said

The report compared the following batch-16 values:

```text
Short prompt:
reported_tok_s = 883.2

Long prompt:
reported_tok_s = 1311.4
```

It interpreted the higher long-prompt number as evidence that longer prompts achieved better throughput.

However, calculating actual generated-token goodput gives:

### Short prompt

```text
batch = 16
prompt = 512
generation = 256
wall clock = 13.91 s
```

```text
16 × 256 / 13.91
= 294.46 output tok/s
```

### Long prompt

```text
batch = 16
prompt = 3584
generation = 512
wall clock = 49.97 s
```

```text
16 × 512 / 49.97
= 163.94 output tok/s
```

Therefore:

| Workload | Reported tok/s | Honest output goodput |
|---|---:|---:|
| Batch 16, prompt 512 | 883.2 | 294.46 tok/s |
| Batch 16, prompt 3584 | 1311.4 | 163.94 tok/s |

The long-prompt workload therefore has lower output-token goodput, despite having a higher value in the `reported_tok_s` column.

## What the report should have said

The report should have stated that the long-prompt row has a higher total token processing rate because its metric includes the 3584 input tokens, but it does not have higher output-generation goodput.

For serving-generation performance, the relevant value is:

```text
generated tokens / wall-clock time
```

For the batch-24 long-prompt row, this is approximately:

**200.9 output tok/s.**

Therefore, `reported_tok_s` should not be interpreted as output-generation throughput.
